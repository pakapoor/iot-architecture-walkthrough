WHY IT'S BUILT THIS WAY
⏱ Timers, not polling
"Device down > X min" is a per-device timer in Flink state. No scanning 100M rows in a DB — why Flink beat Kinesis + Lambda.
🚨 Two alert lanes
Critical pages on-call instantly. Minor issues roll into 15-min site digests. No alert storms, no 3 AM pings.
🔁 Idempotent actions
Incident ID = tenant + device + outage generation. Retries upsert the same ticket; failures go to a DLQ with alarms. No duplicate tickets.
💰 Pay for what's hot
7 days hot for live views, 6-month rollups, sampled cold archive. Tiered retention bounds hot-storage cost per device.
🛟 Degrade, don't die
Edge buffers through outages, standby gateway takes over, Kafka replays. Bounded buffering + failover; recovery is monitored.
Observability: consumer lag · checkpoint health · throughput · end-to-end trace ID (edge → ticket)
Deployment: independent services on K8s · global region + isolated China region

WHY TEMPORAL HERE
🎯 One ticket per incident
Duplicate alerts land on the same workflow ID, so they update the open ticket instead of creating new ones.
🔁 Retries that survive outages
Workflow state is durable. Workers crash, ServiceNow goes down for hours — it resumes exactly where it stopped.
⏰ Escalation is code, not cron
"No ack in 30 min → page L2" is a timer inside the workflow. No polling jobs, no scheduler tables.
💤 Waits days, not seconds
A field fix can take 2 days. The workflow sleeps durably until ServiceNow says "closed".
Before: SQS → DLQ → handler + cron for retries and escalation  ·  After: one durable workflow owns the whole incident lifecycle
